# Reports (`backend/reports/`)

Reproducible, committed validation and audit output — Quran-source/database
validation, cleanup dry-runs, and emotion-mapping candidate/consolidation
reports. Every file here is generated by re-running the corresponding script
and is safe to check in: none of them contain database credentials,
connection strings, or destructive-operation payloads.

| Directory | Contents |
| --- | --- |
| `quran-data/` | `npm run validate:quran:source` / `validate:quran` / `import:quran` output (`source-validation.json`, `database-validation.json`, `preflight.json`), plus the frozen Phase 3 baseline/comparison/regression records and `summary.md`. |
| `data-cleanup/` | `cleanup-dry-run.json` from `backend/src/scripts/prepareArabicCleanup.ts` — a dry-run report of what a future MongoDB Arabic-field cleanup would change. **Always a report, never a backup** — see below. |
| `emotion-mappings/` | `npm run mapping:candidates` output and the Phase 5C consolidated-mapping validation report. |

## Reports are not backups

`backend/reports/` is for **reproducible output**: re-running the same
script against the same data regenerates the same report. It is **not**
where pre-destructive-operation backups go.

Two scripts perform a real, irreversible MongoDB mutation gated behind an
explicit flag (`fullQuran.ts --write`, `prepareArabicCleanup.ts --destructive
--confirm-irreversible`). Immediately before either mutation, each writes a
full backup of the data it is about to change — that backup is a one-time,
point-in-time safety copy, not a report, and belongs outside `reports/`:

```text
backend/backups/
├── quran-data/
│   └── before-write-<timestamp>.json          (fullQuran.ts --write)
└── data-cleanup/
    └── mongodb-arabic-before-cleanup-<timestamp>.json  (prepareArabicCleanup.ts --destructive)
```

`backend/backups/` is entirely git-ignored (`backend/backups/.gitignore`
contains only `*` / `!.gitignore`) — its contents must never be committed.
As of this writing **no real backup exists yet**; only `.gitignore` is
present.

### Side-effect-free destination constants

Both scripts resolve their backup/report destinations from
`backend/src/utils/backupPaths.ts` (`QURAN_DATA_BACKUPS_DIR`,
`ARABIC_CLEANUP_BACKUPS_DIR`, `CLEANUP_DRY_RUN_REPORT_PATH`) rather than
computing the path themselves. That module does nothing but resolve three
absolute paths from its own file location — importing it never loads the
Quran corpus, connects to MongoDB, writes a file, or inspects CLI
arguments, so it is independently unit-tested
(`backend/tests/quran-data/backup-paths.test.ts`) even when
`backend/data/quran/quran-data.xml` is absent from the local checkout.
(That legacy XML is an unrelated, separate concern: it is **not** the King
Fahd verification source, and nothing in this backup-path work restores,
regenerates, or depends on it.)

### Write, verify, and restore

Both scripts write their backup using the shared `writeVerifiedJsonBackup`
helper (`backend/src/utils/backupFile.ts`), which:

- creates the destination directory recursively;
- writes with fail-if-exists semantics (`flag: 'wx'`) so an existing backup
  is never silently overwritten;
- immediately reads the backup back, parses it as JSON, and checks its
  shape/record count against what was actually fetched;
- computes and returns a SHA-256 of the exact bytes written;
- throws before returning if any of the above fails — the calling script
  never proceeds to the database mutation in that case.

Every record in a Mongo-document backup carries a real `_id`
(`mongoose.Types.ObjectId`). `backend/src/utils/objectId.ts` makes that
identity explicitly reconstructible rather than merely present:

- **Format version 1, `objectIdEncoding: "hex24"`** — both scripts wrap
  their payload as `{ formatVersion: 1, objectIdEncoding: "hex24", records }`
  before handing it to `writeVerifiedJsonBackup`. This documents, rather than
  leaves implicit, that `JSON.stringify` on a real ObjectId already produces
  its plain 24-character lowercase hex string (via `ObjectId#toJSON`) — the
  format this repository actually writes today.
- **Reconstruction:** `decodeObjectIdHex(hex)` strictly validates the string
  (exactly 24 hex characters) and returns `new mongoose.Types.ObjectId(hex)`
  — the same type and value as the original, never a plain string. It
  rejects a missing, `null`, wrong-length, non-hex, or otherwise
  unrecognizable value instead of silently coercing it.
- **Verification before mutation:** both scripts' backup `validate`
  callback calls `recordsRoundTripObjectIds(originalRecords, parsedRecords)`,
  which re-encodes each original document's `_id`, decodes the
  corresponding parsed record's `_id` back into a real `ObjectId`, and
  requires the two to be exactly equal (and unique) for every record —
  proven for a deterministic ObjectId end-to-end through a real file write
  in `backend/tests/quran-data/object-id.test.ts`. As with the shape check
  this replaced, a failure throws before either script's destructive
  transaction can start.
- No new dependency was added for this: `mongoose.Types.ObjectId` is the
  same BSON `ObjectId` class the repository's existing direct `mongoose`
  dependency already exposes.

`reports/data-cleanup/cleanup-dry-run.json` is unaffected by any of this
and stays exactly where it was: it is the dry-run **report**, not the
destructive-mode backup, and Phase 4C's cleanup has not been
executed — destructively or otherwise — by this correction.
