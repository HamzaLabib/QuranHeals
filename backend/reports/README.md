# Reports (`backend/reports/`)

Reproducible, committed validation and audit output — Quran/translation
source and database validation, cleanup dry-runs, and emotion-mapping
candidate/approval/activation reports. Every file here is generated by
re-running the corresponding script and is safe to check in: none of them
contain database credentials, connection strings, or destructive-operation
payloads.

| Directory | Contents |
| --- | --- |
| `cleanup/` | Cleanup and migration safety reports, including dry-run outputs — `cleanup-dry-run.json` (`prepareArabicCleanup.ts`) and `translation-cleanup-dry-run.json` (`prepareTranslationCleanup.ts`). **Always a report, never a backup** — see below. |
| `emotion-mappings/` | Candidate, approved and activation-verification reports for emotion-to-ayah mappings: `candidate-mappings.*`, `approved-mappings.*`, and `activation-dry-run.*`. |
| `quran-verification/` | Quran and translation source validation, database integrity, comparison, regression and runtime-verification reports — `source-validation.json`, `database-validation.json`, `preflight.json`, `api-regression.json`, the Gutenberg-Pickthall translation verification, and `runtime/` (browser/export/live-audit checks). |

## Reports are not backups

`backend/reports/` is for **reproducible output**: re-running the same
script against the same data regenerates the same report. It is **not**
where pre-destructive-operation backups go.

Scripts that perform a real, irreversible MongoDB mutation do so behind an
explicit flag (`fullQuran.ts --write`, `prepareArabicCleanup.ts --destructive
--confirm-irreversible`, `prepareTranslationCleanup.ts --destructive
--confirm-irreversible`). Immediately before any such mutation, the script
writes a full backup of the data it is about to change — that backup is a
one-time, point-in-time safety copy, not a report, and belongs outside
`reports/`:

```text
backend/backups/
├── quran-data/
│   └── before-write-<timestamp>.json                       (fullQuran.ts --write)
├── data-cleanup/
│   └── mongodb-arabic-before-cleanup-<timestamp>.json       (prepareArabicCleanup.ts --destructive)
└── translation-cleanup/
    └── mongodb-translation-before-cleanup-<timestamp>.json  (prepareTranslationCleanup.ts --destructive)
```

`backend/backups/` is entirely git-ignored (`backend/backups/.gitignore`
contains only `*` / `!.gitignore`) — its contents must never be committed.
See [the runtime architecture doc](../../docs/quran-architecture/runtime-architecture.md)
for which cleanups have actually been run, their backups' SHA-256s, and the
rollback procedures (including the current, honestly-documented status of
each backup file's local availability).

### Side-effect-free destination constants

Cleanup scripts resolve their backup/report destinations from
`backend/src/utils/backupPaths.ts` (`QURAN_DATA_BACKUPS_DIR`,
`ARABIC_CLEANUP_BACKUPS_DIR`, `CLEANUP_DRY_RUN_REPORT_PATH`,
`TRANSLATION_CLEANUP_BACKUPS_DIR`, `TRANSLATION_CLEANUP_DRY_RUN_REPORT_PATH`)
rather than computing the path themselves. That module does nothing but
resolve absolute paths from its own file location — importing it never loads
the Quran corpus, connects to MongoDB, writes a file, or inspects CLI
arguments, so it is independently unit-tested
(`backend/tests/quran-data/backup-paths.test.ts`) even when
`backend/data/quran/quran-data.xml` is absent from the local checkout.
(That legacy XML is an unrelated, separate concern: it is **not** the King
Fahd verification source, and nothing in this backup-path work restores,
regenerates, or depends on it.)

### Write, verify, and restore

Backup-writing scripts use the shared `writeVerifiedJsonBackup` helper
(`backend/src/utils/backupFile.ts`), which:

- creates the destination directory recursively;
- writes with fail-if-exists semantics (`flag: 'wx'`) so an existing backup
  is never silently overwritten;
- immediately reads the backup back, parses it as JSON, and checks its
  shape/record count against what was actually fetched;
- computes and returns a SHA-256 of the exact bytes written;
- throws before returning if any of the above fails — the calling script
  never proceeds to the database mutation in that case.

Every record in a Mongo-document backup carries a real `_id`
(`mongoose.Types.ObjectId`). `backend/src/utils/objectId.ts` makes that
identity explicitly reconstructible rather than merely present:

- **Format version 1, `objectIdEncoding: "hex24"`** — backup-writing scripts
  wrap their payload as `{ formatVersion: 1, objectIdEncoding: "hex24",
  records }` before handing it to `writeVerifiedJsonBackup`. This documents,
  rather than leaves implicit, that `JSON.stringify` on a real ObjectId
  already produces its plain 24-character lowercase hex string (via
  `ObjectId#toJSON`) — the format this repository actually writes today.
- **Reconstruction:** `decodeObjectIdHex(hex)` strictly validates the string
  (exactly 24 hex characters) and returns `new mongoose.Types.ObjectId(hex)`
  — the same type and value as the original, never a plain string. It
  rejects a missing, `null`, wrong-length, non-hex, or otherwise
  unrecognizable value instead of silently coercing it.
- **Verification before mutation:** each script's backup `validate` callback
  calls `recordsRoundTripObjectIds(originalRecords, parsedRecords)`, which
  re-encodes each original document's `_id`, decodes the corresponding
  parsed record's `_id` back into a real `ObjectId`, and requires the two to
  be exactly equal (and unique) for every record — proven for a
  deterministic ObjectId end-to-end through a real file write in
  `backend/tests/quran-data/object-id.test.ts`. A failure throws before the
  destructive transaction can start.
- No extra dependency is needed for this: `mongoose.Types.ObjectId` is the
  same BSON `ObjectId` class the repository's existing direct `mongoose`
  dependency already exposes.

`reports/cleanup/cleanup-dry-run.json` and
`reports/cleanup/translation-cleanup-dry-run.json` are unaffected by any of
this and stay exactly where they are: dry-run/last-run **reports**, never
destructive-mode backups.
